# Google Cloud production delivery

Production source branch: `deploy/gcp` in `axxes-club/members.axxes.club`. Pushes to this branch run the `GCP production` workflow. Main and other branches do not deploy. GitHub manual dispatch requires the workflow on the default branch; this configuration remains on `deploy/gcp`, so use production pushes until an approved integration makes manual dispatch available.

GitHub only checks out source and exchanges its OIDC identity for short-lived credentials. Google Cloud Build performs Linux image builds, configured unit tests/type checks, image publication, staged readiness checks and deployment. No service-account keys, PATs or Vercel deploy hooks are used. Actions are pinned to commit IDs.

Build identity `cb-members` is scoped to `members` Cloud Run service, its runtime account, isolated `ci-members` image repository and source bucket. It reads only members-env from Secret Manager. Submit identity `gh-members` may submit/get builds, upload source and act as this build identity. Federation accepts only this immutable GitHub repository ID and `deploy/gcp` push/manual events.

Images are tagged with the full Git commit SHA and unique Google build ID and deployed by immutable digest. The release changes the image only and preserves runtime settings, secrets and IAM. It first stages a tagged revision with no traffic, probes its root for a 2xx/3xx response, then promotes it and probes the ordinary service URL. Redirect probes reject missing locations, insecure absolute URLs and local/private IP destinations. A failed post-deployment probe restores the previous revision. Existing traffic splits block automatic promotion for an explicit rollout decision. These root probes establish HTTP availability; authentication, payment, upload and database integration checks remain separate release evidence.

Checks in addition to Linux production image build: no unit test/typecheck script exists in this source; Linux image build and HTTP readiness run.

Build logs: https://console.cloud.google.com/cloud-build/builds;region=global?project=gravy-meta

Legacy `Create Release` workflow is disabled at the repository level because its default-branch/tag definition still deploys Vercel. This branch removes that deployment step. GitHub release publishing can resume after the safe release definition is available on the intended tag source/default branch; production app delivery uses the GCP workflow.

BuildKit mounts the production dotenv only during Next compilation; it is excluded from COPY and removed from standalone output before final-image COPY. Every image is exported and all layers are inspected before publication. The gate rejects dotenv files (including files deleted by later layers) and matches private build-secret values without logging them; public NEXT_PUBLIC values are intentionally allowed. Test containers receive only a synthetic AUTH_SECRET and never production dotenv credentials.

Google Cloud Build uses the global build pool; Cloud Run, source buckets and image registries remain in us-west1. The regional build pool allowed only one highcpu8 job, so global capacity avoids long production queues. GitHub jobs allow60minutes and poll for55minutes; failures, cancellation signals or polling deadline cancel unfinished remote builds instead of leaving queued deployments detached. The submit identity includes build cancellation permission for this lifecycle.

The read-only schema gate uses the active mounted secret. Native `/cloudsql/PROJECT:REGION:INSTANCE` URLs now start Cloud SQL Auth Proxy 2.26.0 inside the temporary CI container on the Cloud Build network with application default credentials. Only the gate connection is mapped to loopback port 15432; runtime secrets remain unchanged. The app-scoped Cloud Build service account needs `roles/cloudsql.client`, SQL Admin API enabled, and public-IP reachability (private-only instances require a VPC private pool). Credentials and proxy logs are never printed; proxy startup, authentication, or required schema failures block release. The proxy binary is mounted read-only and removed before push.

The independent main-triggered GCP staging v2 workflow deploys `members-v2` using `cloudbuild-v2.yaml` and `Dockerfile.v2`. Build inputs privately merge `members-v2-env` then `v2-db-env`; the database overlay supplies authoritative DATABASE_URL while product public origins remain intact. Runtime loads the same two mounts in that order and requires both. Staging images use the separate immutable `ci-members-v2/members-v2` repository. No production database or runtime settings are changed by this workflow.

Gangstarz native commerce uses the canonical orders/items/attendees tables plus the reviewed additive `db/gangstarz-commerce.sql` ledgers. Authorized owners/admins configure existing inventory, fulfillment/tax policy, and verified workspace-bound Tollbooth credentials at `/website/gangstarz/commerce`. Credentials use authenticated encryption under `COMMERCE_CREDENTIAL_KEY` (or existing `BETTER_AUTH_SECRET`); retain that key across deployments and plan credential re-encryption before rotating it. Provider notifications go to `/api/v1/public/tenants/gangstarz/commerce/webhook`; signature verification is followed by an authoritative provider read. The authenticated `/api/cron/commerce` reconciliation endpoint recovers delayed attachment/status notifications without issuing charges. Configure one active-authority scheduler using existing CRON_SECRET; do not schedule against the fenced source.

Missing merchant readiness keeps native sales unavailable and preserves existing external ticket links. Test/live merchant modes are separate. Full refunds invalidate tickets; stock returns require explicit received-return records. Neither deployed code nor migration creates financial accounts, grants entitlements, or selects customer prices.

Paid storage remains gated on approved package/price/currency/cadence/expiry/refund terms and legitimate merchant access. `STORAGE_BILLING_CATALOG` accepts only validated, explicit USD one-time terms supported by the current checkout provider; recurring billing requires its corresponding provider lifecycle implementation. Missing/invalid configuration publishes no packages. This catalog does not grant capacity. Run `STORAGE_ROLLOUT_AUDIT=read-only node scripts/storage/rollout.mjs` with the active authority privately supplied to check decimal-exact accounting divergence before enforcement; physical receipt provenance still requires the separate `backfill.mjs` dry-run/review. Keep quota mode off until both entry points use the same active database, reconciliation is reviewed, and owned synthetic live admission tests pass.
